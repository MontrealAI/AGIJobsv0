# External manual signing for a new paused Jobs stack

This native source path separates the creation address from a wallet SDK or private key. It prepares one exact type-2 transaction, stops, and accepts a separately supplied manual signature. It does not sign, broadcast, manage balances, or activate the stack. Hardware/device and trusted-Mac/two-machine qualification are separate acceptance gates; passing source tests alone does not satisfy them.

## Scope and trust

The authoritative driver, reviewed source, original private session, source checks, sender lease, signature import and receipt acceptance run on the trusted operator machine. An experimental Ubuntu machine may propose plain data or relay the exact capability already released by an explicit authorization. Its source, journal, receipt or success response cannot advance the authoritative session. The operator independently selects the read provider; requests cannot choose an RPC URL or module.

The first profile accepts an empty-code creator and ordinary type-2 transactions. There is no on-chain wallet allowlist. Any wallet supported by that profile may be selected before signing. Existing delegated-EOA origin behavior, smart-account execution and hardware devices need their own acceptance evidence. No delegation authorization is created, cleared or invoked. A creator switch regenerates the reviewed configuration, nonces, predicted addresses, plan and session. An existing signing request, signed capability or ambiguous submission must be reconciled first.

The tax-enabled route has exactly 39 creator operations: one coordinator CREATE, ten implementation CREATEs, fourteen source-bound component deployments, configuration commitment, registration, paused finalization, ten implementation ownership transfers and the coordinator ownership transfer. Each operation needs its own exact review and manual signature. Governor acceptance, treasury commissioning, ENS actions, funding, admission and unpause are outside this profile. Existing v1 direct/local journals keep their original semantics; external reports use authorityJournalVersion 2 and cannot be reinterpreted as direct journals.

## Review inputs before loading the runtime

Independently qualify the exact source commit/tree, complete executable and dependency closure, Node executable, installed dependency bytes, archived compiler input/output and config resolution. The native manifest check is a drift guard, not a bootstrap or source-approval oracle. A lockfile or a checksum generated by the running checkout cannot approve itself. The trusted bootstrap must validate these inputs before executing Hardhat or Jobs modules.

Keep the profile, raw deployment config, plan, manifest, commands and session in an owner-only real directory outside the checkout. Signed raw bytes are transaction capabilities. Never put them in Git, stdout, logs, browser storage, public reports or an unreviewed support bundle.

The strict profile contains exactly:

- profile: `jobs-external-manual-v1`
- sessionDirectory: a new absolute private directory, or the original directory for continuation
- planFile: the absolute original reviewed plan
- reviewedPlanHash: keccak256 of the canonical reviewed plan JSON
- sourceManifestFile: the exact independently reviewed manifest
- reviewedSourceManifestSha256: lowercase SHA-256 of its exact bytes

The manifest uses schema `jobs-reviewed-source-v1`, exact sourceCommit/sourceTree, and unique `files` entries containing relative path, SHA-256 and Git regular-file mode (`100644` or `100755`). Required native files are checked in addition to the independently reviewed full closure. Changed bytes, paths, modes, owner/inodes, config or manifest stop the session. Signing keys, mnemonic/account environment settings and runtime override environment settings are rejected. Public Hardhat network accounts must be an empty array.

The plan schema is `jobs-external-plan-v1`. All fields are explicit: campaignId, chainId, creator, governor, sourceCommit, sourceTree, compilerInputSha256, sourceManifestHash, configHash (SHA-256 with `0x` prefix), creationScopeHash (canonical JSON keccak256), firstNonce, creatorCodeHash, initialBlock `{number,hash}`, confirmations, expiresAt, fees `{gasLimit,maxFeePerGas,maxPriorityFeePerGas}` and lockDirectory. The current schema uses the same explicitly reviewed fee/gas envelope for each operation. There are no default production values or automatic fee/nonce updates.

Use the same canonical shared lock directory as other deployment repositories. The actual sender key is `<chainId>-<lowercase-address>` and owner schema is `creator-nonce-lock-v1`. The lease is retained across manual steps and on failure. It is cooperative protection on that filesystem; the operator must prevent concurrent signing on other machines or out of band. Completion does not automatically erase that lease or signed evidence.

## Native prepare/stop/continue workflow

Set DEPLOY_DEFAULTS_CONFIG to the absolute private reviewed config, DEPLOYMENT_EXTERNAL_PROFILE to the private profile, and DEPLOY_DEFAULTS_OUTPUT to a fresh evidence file. Run the existing staged entrypoint with the reviewed runtime and archived artifacts (`hardhat run --no-compile scripts/v2/deployDefaults.ts --network <reviewed-network>`). It selects the address-only signer and stops at `awaiting-external-manual-signature`. It never falls back to an unlocked account or private key. Local external rehearsals require the token fixture to exist already; this path does not install or fund it.

Continue only from the original session and staged evidence. Set the recorded coordinator/predicted coordinator as DEPLOYER_ADDRESS, the original complete report or checkpoint as DEPLOY_DEFAULTS_RESUME_EVIDENCE, and use a fresh output filename. The same config, plan, source, campaign and canonical creation provenance are required. Historical addressbooks and previous deployments cannot authorize this route.

For private session commands, set DEPLOYMENT_EXTERNAL_COMMAND_FILE to a fresh owner-only JSON request, then run `hardhat run --no-compile scripts/v2/externalManual.ts --network <same-reviewed-network>`. Each command writes its result to a fresh private `output` file and prints only safe status. The request supports only:

1. `inspect`: bounded state, unsigned/policy hashes and journal head. No raw signature.
2. `handoff`, with independently reviewed `{planHash,unsignedHash,policyHash}`: persists the signing-requested marker before returning the exact unsigned envelope.
3. `retrieve`: recovers the original handoff without granting a new signing request.
4. `import-signed`, with a private signedFile containing exactly `{ "raw": "0x..." }`: validates canonical serialization, recovered sender and every field. An identical repeated import recovers the original acknowledgement; a different signature/capability is rejected.
5. `authorize-relay`, with the exact returned relay acknowledgement: checks current source, lease, chain, nonce, expiry and canonical prefix, then persists an immutable attempt before writing raw bytes to the private output. It performs no network send. Only the operator-controlled relay may submit those exact bytes.
6. `observe`: independently reads the expected transaction and successful canonical receipt. A mined unknown-hash signing request uses a bounded exact sender/nonce/envelope scan. It never resends.
7. `recover-command`: first inspect the retained guard; explicitly stop the prior trusted executor, then provide its exact acknowledgement to clear only that original guard. It does not remove the actor lease, journal or capability.
8. `repair-head`: after command recovery, explicitly acknowledge a single complete interrupted journal append. A torn/reordered record or different head remains blocked.

Private journal events use schema `jobs-external-event-sha256-v1`: `hash` is `0x` plus native SHA-256 of canonical JSON of every event field except `hash`, including the schema, sequence, previousHash, planHash, action, index and details. The `jobs-external-head-sha256-v1` head binds that exact event hash. Every reread recomputes event hashes; the bounded read cache is keyed only by a recomputed valid event hash. Exact envelopes are fully revalidated at signing handoff/retrieval, signature import, relay authorization and canonical transaction acceptance. This new private format does not alter v1 direct/local journal semantics. Plan and Ethereum envelope/policy hashes remain keccak256.

The prepared packet is `jobs-external-envelope-v1`: exact source/campaign/config/plan/scope/operation context, full transaction, unsignedHex, unsignedHash and policyHash. Full transaction fields are type=2, chainId, nonce, to/null, zero value, calldata, gasLimit, maxFeePerGas, maxPriorityFeePerGas and an empty access list. Unknown fields, other transaction types and authorization lists are rejected. No generic `prepare` request accepts externally supplied calldata; the staged writer regenerates it from the reviewed source and config.

A lost response never authorizes another signature or relay. “One authorized attempt” cannot guarantee exactly-once network delivery or stop a recipient who already holds signed bytes. Local expiry cannot revoke an Ethereum signature. Expired capabilities remain retained for observation/reconciliation. Reorgs, replacements, failed receipts, unexpected pending nonces, wallet code drift or mismatched owners stop progress. A completed paused stack still has false productionApproved and activationReady flags and requires separate commissioning and complete provenance/explorer qualification.

Incomplete initialization, a malformed/partial command-owner record, a torn event, or an unrecoverable head mismatch is deliberately not repaired automatically. Stop the prior executor, preserve the entire original private directory and shared lease, and obtain an exact reviewed recovery procedure. Do not delete a lock, copy state into a new campaign, reset a nonce or sign again merely because a command did not return. An entirely empty command guard has an explicit stopped-executor recovery bound to its current inode, exact empty membership, original session/lease and journal head. The supported recover-command/head-repair APIs require intact identity evidence; they do not claim recovery from every filesystem failure.
